## Зафиксированные решения

### 2026-09-27 — Демо-режим для жюри с эмулятором событий

- **Контекст:** жюри должно оценить приложение без аккаунта MAX и без реальных учеников, причём увидеть живые сценарии: модерацию, проверку работ, чат.
- **Решение:** `DEMO_MODE` включает вход по ролям в демо-академию и панель эмулятора. События создаются через те же use cases, что и в приложении, от имени демо-пользователей с ID вне диапазона MAX; эмулятор не отправляет сообщений в MAX.
- **Причина:** жюри видит настоящую логику (уведомления, права, статусы), а не заглушки; реальные пользователи и бот не затрагиваются.
- **Последствия:** демо-администратор видит всех пользователей инстанса, поэтому демо включается только на стенде для хакатона. Демо-данные создаются один раз; для сброса нужно удалить демо-пользователей и перезапустить API.

### 2026-09-25 — Docker: отдельные сервисы web, api и bot

- **Контекст:** требования хакатона MAX: запуск одной командой, в конфигурации только необходимые компоненты.
- **Решение:** `web` (nginx со статикой клиента и прокси `/api`), `api` (NestJS) и `bot` (тот же образ backend, `node dist/bot-main.js`). Схема создаётся из `backend/prisma/schema.sql` при старте `api`, если база пустая. Переменные передаются через `x-app-env` из `.env` или окружения платформы.
- **Причина:** бот не должен дублировать long polling при масштабировании API; один образ backend исключает расхождение кода API и бота.
- **Последствия:** без `MAX_BOT_TOKEN` бот завершается с кодом 0 и не перезапускается, сайт и API работают. Первого администратора пока назначают вручную в SQLite.

### 2026-09-24 — Визуальные регрессионные тесты клиента со строгим сравнением

- **Контекст:** интерфейс плотный, много состояний; ручная проверка после каждой правки не масштабируется.
- **Решение:** Playwright-снимки экранов и поведенческие сценарии на стенде NestJS с детерминированным сидом; сравнение с `threshold: 0`, 4 проекта (`light`/`dark` × 390/360).
- **Причина:** попиксельное сравнение делает изменения интерфейса видимыми в ревью, а не декларируемыми.
- **Последствия:** эталоны пересобираются только осознанно (`npm run visual:update`); внешние скрипты, включая MAX Bridge, в тестах заглушены.

### 2026-09-23 — Файлы хранятся в S3-совместимом хранилище

- **Контекст:** приложение разворачивается на хостинге, где локальный диск контейнера не должен быть единственным местом хранения работ учеников.
- **Решение:** абстракция `ObjectStorage` с драйверами S3 (`@aws-sdk/client-s3`) и локального каталога для разработки и тестов. В БД хранится ключ объекта; входящий файл проходит через временный каталог, где `sharp` перекодирует изображения. Файлы отдаются только через API с проверкой прав, публичных ссылок на бакет нет.
- **Причина:** права доступа к работам проверяет backend; S3 отделяет данные от жизненного цикла контейнера.
- **Последствия:** `has_file` в ответах означает наличие корректного ключа — проверка существования объекта на каждый элемент списка была бы дорогой; отсутствующий объект даёт 404 при скачивании. Витрина проверяет существование только у выбираемых кандидатов.

### 2026-09-22 — Вход на сайт через подтверждение в боте MAX

- **Контекст:** дневник должен работать и как обычный сайт, без пароля и SMS.
- **Решение:** сайт создаёт одноразовый запрос и открывает `https://max.ru/<бот>?start=webauth_<token>`; бот подтверждает вход от имени пользователя MAX, сайт опросом получает web-сессию. В БД хранятся только SHA-256 хэши токенов.
- **Причина:** используется уже существующий аккаунт MAX; не нужны пароли и отдельная регистрация.
- **Последствия:** нужен `MAX_BOT_USERNAME`. Payload ссылки ограничен 128 символами, токен укладывается в этот лимит.

### 2026-09-21 — Бот — мессенджер-независимое ядро с адаптером MAX

- **Контекст:** бот дублирует ключевые действия (подтверждение входа, модерация, роли, проверка ДЗ, приглашения к отзыву) и не должен расходиться с проверками API.
- **Решение:** сценарии живут в `backend/src/messenger/` и работают через абстрактный канал (команды, сообщения, нажатия кнопок; исходящие текст, медиа и кнопки) поверх тех же use cases, что HTTP API. MAX-адаптер реализует канал через MAX Bot API на `fetch` (long polling `/updates`, `/messages`, `/answers`, `/uploads`).
- **Причина:** общие use cases исключают обход проверок прав и аудита; тонкий клиент на `fetch` проще тестировать поддельным сервером.
- **Последствия:** ответ в диалог идёт по `chat_id`, личные уведомления — по `user_id`. Состояние диалогов хранится в памяти процесса бота.

### 2026-09-20 — Фотография профиля ученика видна другим ролям

- **Контекст:** аватар ученика должен быть виден его преподавателям, администратору и в гостевой витрине.
- **Решение:** `/api/students/:id/avatar` для ученика, его преподавателей и администратора и публичный `/api/guest/students/:id/avatar` для витрины; во все ответы с данными ученика добавлен `has_avatar`.
- **Причина:** портфолио теряет смысл без лица автора работ.
- **Последствия:** фотография ученика со статусом `studying` доступна без авторизации как часть витрины. Гостевой ответ кэшируется как `public`, ролевой — как `private`.

### 2026-09-19 — Снятие роли преподавателя сохраняет историю

- **Контекст:** удаление строки `teachers` каскадно удалило бы назначения и все проверки преподавателя.
- **Решение:** снятие роли удаляет только `user_roles.teacher` и текущие `student_teachers`; профиль и проверки сохраняются. Активный преподаватель — пользователь с ролью `teacher`, повторное назначение переиспользует профиль.
- **Причина:** проверки — учебная история ученика.
- **Последствия:** административные списки, session и teacher use cases учитывают активную роль, а не только наличие строки `teachers`.

### 2026-09-18 — Конфиденциальная обратная связь ученика

- **Контекст:** ученику нужен безопасный канал для пожеланий о преподавателе и академии.
- **Решение:** отзыв отправляется отдельной формой и доступен только ученику при отправке и администраторам при просмотре. После принятия уроков 5, 10 и 15 бот приглашает ученика оставить отзыв.
- **Причина:** преподаватель не должен получать текст или уведомление об отзыве.
- **Последствия:** отзывы не анонимны для администратора. Таблицы `private_feedback` и `feedback_invites` не использовать как часть чатов или портфолио.

### 2026-09-17 — Роли, уровни обучения и публичная витрина

- **Контекст:** нужен единый сайт с разными правами и наглядным разделением пути ученика.
- **Решение:** вход для ученика, преподавателя и администратора; гость открывает публичную витрину по ссылке без авторизации. Учеников разделяют уровни «Ученик», «Стажёр», «Барбер».
- **Причина:** публичное портфолио отделено от учебных данных.
- **Последствия:** контакты, никнеймы и служебные идентификаторы не передаются гостю. При уровне «Барбер» привязки к преподавателям снимаются автоматически.

### 2026-09-16 — Личность определяется подписанным credential, а не полем max_user_id

- **Контекст:** клиент передаёт `max_user_id` в query/body, но это поле само по себе не подтверждает личность.
- **Решение:** authentication guard сверяет `max_user_id` с подписанным initData мини-приложения MAX (`X-Max-Init-Data`, HMAC-SHA256 от токена бота) либо с web-сессией и передаёт use case `CurrentPrincipal`. Проверки ролей — в отдельном guard. `users.max_user_id` в Prisma — `BigInt`.
- **Причина:** единая граница авторизации исключает доверие пользовательскому полю.
- **Последствия:** в production `MAX_WEBAPP_AUTH=strict`; режим `optional` допустим только для локальной разработки в браузере.

### 2026-09-16 — Схема SQLite задаётся schema.sql, Prisma её отражает

- **Контекст:** нужна простая схема для хакатона без отдельного процесса миграций.
- **Решение:** `backend/prisma/schema.sql` применяется только к пустой базе (`init-schema.ts`), `schema.prisma` ей соответствует; `prisma migrate` и `db push` не используются.
- **Причина:** один источник структуры и предсказуемый старт в Docker.
- **Последствия:** изменение схемы вносится в оба файла; e2e-тест сверяет таблицы. Миграции существующих баз не выполняются.

### 2026-09-15 — Стек: NestJS + Fastify, Prisma, React 19

- **Контекст:** веб-приложение и мини-приложение MAX с ботом, загрузкой фото и видео и строгими правами доступа.
- **Решение:** backend — NestJS с Fastify adapter, TypeScript, Prisma поверх SQLite (`backend/`); клиент — React 19, TypeScript, Vite, Zustand, TanStack Query (`frontend/`). Один билд клиента работает как сайт и как мини-приложение MAX.
- **Причина:** модульная структура NestJS и общий TypeScript на обеих сторонах; Fastify удобен для multipart и потоковой отдачи файлов.
- **Последствия:** backend и frontend — отдельные пакеты со своими зависимостями и сборкой.

### 2026-09-15 — Постоянная память проекта хранится в репозитории

- **Контекст:** нужно сохранять важный контекст между задачами, не перечитывая весь код.
- **Решение:** использовать `PROJECT_CONTEXT.md`, этот журнал, `QUALITY_RULES.md` и правила в `AGENTS.md`.
- **Причина:** документы доступны при следующей задаче, проверяемы и обновляются вместе с проектом.
- **Последствия:** существенные решения необходимо кратко фиксировать в этом журнале.
