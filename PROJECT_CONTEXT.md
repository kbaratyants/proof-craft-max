# Дневник академии — контекст проекта

## Назначение

**Дневник академии** — веб-приложение для барбер-академии, доступное как обычный сайт и как мини-приложение MAX. На сайте пользователь подтверждает вход в боте MAX. Оно сопровождает путь ученика: заявка и модерация, обучение, сдача и проверка домашних заданий, коммуникация и уведомления. Бот предоставляет параллельный интерфейс подтверждения входа, модерации, проверки ДЗ и администрирования.

## Технологии

Проект готовится к хакатону MAX.

- Backend: NestJS 12 с Fastify adapter, TypeScript, Prisma 7.10 поверх SQLite (`@prisma/adapter-better-sqlite3`) — `backend/`. Реализованы все 58 маршрутов API.
- Бот: `backend/src/messenger/` — мессенджер-независимые сценарии поверх тех же use cases, что и HTTP API; MAX-адаптер (fetch, long polling MAX Bot API); отдельный процесс `bot-main.ts`.
- Клиент: React 19 + TypeScript + Vite 8, Zustand, TanStack Query — `frontend/`; Один билд работает как сайт и мини-приложение MAX (MAX Bridge `window.WebApp`).
- Изображения: `sharp`. Запуск: Docker Compose (`api`, `bot`, `web` на nginx).

## Роли и основные сценарии

- **Гость:** смотрит публичное портфолио/витрину работ; может подать заявку преподавателя.
- **Ученик:** регистрируется, ожидает модерации, просматривает профиль и ДЗ, отправляет/редактирует ДЗ и доработки, получает уведомления, общается в чате со своей командой, подаёт правки профиля.
- **Преподаватель:** видит закреплённых учеников и их работы, выставляет оценку и комментарий, ведёт чат с учеником.
- **Администратор:** модерирует учеников и заявки преподавателей, назначает преподавателей, управляет карточками учеников/преподавателей, рассматривает изменения профиля, просматривает аудит и уведомления.
- **Бот:** подтверждение входа на сайт, модерация и роли (`/admin`), проверка ДЗ (`/teacher`), приглашения к отзыву.

## Данные и база

- Файл БД задаёт `DATABASE_URL` (в Docker — `/app/data/barber.db` в томе `barber-data`). Пустую базу создаёт `backend/src/database/init-schema.ts` из `backend/prisma/schema.sql`; существующую не меняет, миграций схемы пока нет.
- Основные сущности: `users`, `user_roles`, `students`, `teachers`, `student_teachers`, `homeworks`, `homework_reviews`, `homework_comments`, `homework_files`, `chat_messages`, `app_notifications`, `audit_log`.
- Дополнительные рабочие сущности: `teacher_applications`, `student_profile_edits`, `web_login_requests`, `web_sessions`, `private_feedback`, `feedback_invites`. У профилей ученика и преподавателя есть текстовое поле `about_me`.
- Обратная связь ученика хранится отдельно от чатов и доступна только ученику-автору при отправке и администраторам при просмотре. Преподаватели не получают её через API, уведомления или бот. После принятия уроков 5, 10 и 15 создаётся одно приглашение к отзыву; бот отправляет его при наличии `WEB_APP_URL` с HTTPS.
- Файлы ДЗ, вложения чата и аватары хранятся в S3-совместимом хранилище (`STORAGE_DRIVER=s3`) или, для разработки и тестов, в каталоге `uploads` рядом с файлом БД (`local`). В БД (`file_id`, `avatar_file_id`) записывается ключ объекта (`homeworks/…`, `chat/…`, `avatars/<id>/…`); входящий файл сначала попадает во временный каталог, где `sharp` перекодирует изображения. Признак `has_file` в ответах API означает, что у записи есть корректный ключ; наличие объекта проверяется при скачивании (иначе 404); размер одного загружаемого файла ограничивается настройкой, по умолчанию 450 МБ.
- Публичные файлы и вложения доступны только для `approved`-работ учеников `studying`; storage adapter открывает объект по ключу и генерирует JPEG-preview фото.
- Авторизованная витрина `showcase` выбирает случайные `approved` фото/видео с файлом, реально существующим в хранилище (проверяются только выбираемые кандидаты), исключает повторы по паре «ученик + файл» и циклически дополняет выборку после `exclude_ids`.
- Уведомления берут identity из проверенного credential: `GET /api/notifications` возвращает только записи этого user ID, парсит JSON payload и считает все непрочитанные записи независимо от лимита; `POST /api/notifications/read` отмечает одно или все уведомления только этого пользователя. Retention-cleanup и запись состояния изолированы в application services и Prisma repository.
- `GET /api/student/homeworks` находит профиль только по внутреннему user ID из проверенного credential, возвращает все его работы, проверки, комментарии и вложения и считает рейтинг только по принятым оценкам. Prisma-запрос, файловая доступность и HTTP-контракт разделены между repository, storage adapter и use case.
- `POST /api/homeworks` в `StudentHomeworksModule` принимает текст либо до пяти multipart-файлов, разрешая серии только из изображений. Ученик должен иметь статус `studying`; второй pending для того же урока или бонуса отклоняется. Работа, дополнительные файлы и app-уведомления преподавателям/администраторам фиксируются одной Prisma-транзакцией, уведомление в MAX отправляется после коммита, а файлы очищаются при любой ошибке.
- `GET /api/homeworks/:id/file` отдаёт файл из хранилища и JPEG-preview только владельцу работы, назначенному преподавателю или администратору; проверка назначения выполняется по внутреннему user ID, а безопасное открытие файла остаётся в общем storage adapter.
- `GET /api/homeworks/:homeworkId/revision/file` переиспользует ту же матрицу доступа и storage adapter. Отсутствие ссылки на файл исправления возвращает `404` до проверки прав; существующий файл недоступен постороннему пользователю.
- `GET /api/homeworks/:homeworkId/attachments/:attachmentId/file` проверяет принадлежность вложения работе до проверки прав, затем применяет ту же матрицу доступа и общий storage adapter; JPEG-preview создаётся только для вложений типа `photo`.
- Три read-маршрута `ChatModule` возвращают доступные чаты, историю сообщений и вложения из хранилища. Ученик видит свой чат, администратор — все, а преподаватель только назначенных через `student_teachers`; так в NestJS закрыт `SEC-002`. Validation и флаг `CHAT_ENABLED` проверяются до credential, маппинг ролей отправителей отделён от Prisma repository, файлы открываются общим storage adapter.
- `POST /api/chats/messages` в `ChatModule` принимает multipart-текст и первое вложение, применяет ту же матрицу доступа с исправлением `SEC-002`, безопасно нормализует изображения и атомарно создаёт сообщение с app-уведомлениями. Временный или финальный файл удаляется при ошибке auth/domain/БД; маршрут не выполняет внешних вызовов мессенджера.
- `GET /api/student/me/avatar` связывает проверенный principal со student-профилем по внутреннему user ID и отдаёт JPEG из хранилища через общий storage adapter с private cache.
- `GET /api/students/:student_id/avatar` использует тот же storage adapter, но перед выдачей проверяет по внутреннему user ID, что principal — владелец профиля, назначенный преподаватель или администратор.
- `POST /api/student/me/avatar` принимает поток через `@fastify/multipart`, ограничивает его `MAX_HOMEWORK_UPLOAD_MB`, нормализует изображение в JPEG 400×400 и обновляет Prisma только после успешной записи нового файла. При сбое новый файл удаляется, а прежний аватар сохраняется; после успешного обновления прежний объект удаляется из хранилища.
- `POST /api/student/about` и `POST /api/teacher/about` используют общий ProfilesModule: описание валидируется до credential-проверки, внешние пробелы обрезаются, пустая строка сохраняется как `NULL`. Раздельные use cases выбирают student или teacher только по внутреннему user ID проверенного principal, а записи изолированы в общем Prisma repository.
- `POST /api/student/profile-edit` в ProfilesModule доступен только student-профилям `studying/completed`: одна Prisma-транзакция отклоняет прежнюю pending-заявку и создаёт новую, не изменяя профиль. Аудит, app-уведомления и best-effort доставка в MAX администраторам; внешний вызов MAX изолирован gateway и его ошибка не отменяет заявку.
- `GET /api/admin/profile-edits` в ProfilesModule использует общую точную admin-проверку и возвращает только pending-заявки по `created_at DESC`, объединяя предложенные значения с текущими полями student-профиля и MAX ID пользователя.
- `POST /api/admin/profile-edits/:id` в ProfilesModule транзакционно одобряет либо отклоняет pending-заявку: approve обновляет профиль и заявку вместе, reject сохраняет комментарий, обе ветки фиксируют reviewer и best-effort аудит. Известный дефект `BUG-002`: уведомление ученику не создаётся, reject-событие называется `profile_edit_rejectd`.
- Оставшиеся административные GET собраны в отдельном `AdminModule`: pending-заявки преподавателей, cursor-пагинация приватных отзывов, преподаватели с учениками, списки и полная карточка ученика, работы с проверками/вложениями и аудит. Controller отвечает только за HTTP-границу, семь use cases применяют общую admin-policy, а Prisma repository строит агрегаты; `GET /api/admin/students` исправляет `BUG-001` и точно разделяет `studying`/`completed`.
- `POST /api/admin/students` в `AdminModule` выполняет модерацию и последующие смены статуса. При approve непустой `teacher_ids` дедуплицируется, проверяется и полностью заменяет назначения; для остальных действий поле игнорируется. Статус, назначения, аудит и in-app уведомление фиксируются одной Prisma-транзакцией, уведомление в MAX отправляется после неё через общий gateway.
- `POST /api/admin/teachers` в `AdminModule` назначает и снимает роль преподавателя. Исправление `SEC-003`: деактивация удаляет роль и текущие назначения, но сохраняет teacher-профиль и исторические проверки; session, административные списки и teacher use cases считают активным только пользователя с ролью `teacher`, а повторное назначение переиспользует прежний профиль.
- `POST /api/admin/assign-student` и `POST /api/admin/unassign-student` используют общий use case назначений: активный преподаватель связывается только с учеником `studying/completed`, связь изменяется идемпотентно, а аудит и два app-уведомления записываются атомарно. Уровень `barber` получает успех и уведомления без создания связи; уведомления в MAX отправляются обеим сторонам после коммита.
- `POST /api/admin/update-student` в `AdminModule` частично обновляет число занятий/уровень и полностью заменяет список активных преподавателей; уровень `barber` всегда очищает назначения. Известный дефект `BUG-003`: профиль обновляется до domain-валидации списка преподавателей и при последующей ошибке остаётся частичная запись без аудита.
- `POST /api/admin/teacher-applications` в `AdminModule` атомарно принимает либо отклоняет pending-заявку. Approve создаёт роль и профиль, аудит и in-app уведомление, после коммита отправляет уведомление в MAX; активный существующий преподаватель получает ответ `already_teacher`, а сохранённый деактивированный профиль получает роль обратно по `SEC-003`.
- `POST /api/teacher-application` в новом `RegistrationModule` принимает подтверждённую MAX identity или web-session, нормализует ФИО и телефон, создаёт guest-пользователя при необходимости и атомарно заменяет его pending-заявку. In-app уведомления администраторам входят в транзакцию, уведомление в MAX отправляется после коммита.
- `POST /api/students` в `RegistrationModule` выполняет validation/auth/domain-проверки в фиксированном порядке, нормализует регистрационные данные и одной Prisma-транзакцией создаёт либо обновляет identity, добавляет student-роль, создаёт профиль в moderation и app-уведомления администраторам. Уведомление в MAX отправляется после коммита; повторная заявка возвращает совместимый `409`.
- `POST /api/student/feedback` в том же модуле разрешён только principal с существующим student-профилем и идемпотентно сохраняет приватный отзыв по паре student + `request_key`; преподавателю данные не раскрываются.
- Read-only кабинет преподавателя — `TeacherCabinetModule`: отдельные use cases обслуживают dashboard, список учеников и профиль с работами, а общий Prisma repository скрывает выборки и агрегаты. Преподаватель видит только назначенных учеников в статусах `studying`/`completed`; администратор без teacher-профиля видит всех активных учеников. Если у администратора есть teacher-профиль, действует область его назначений.
- `POST /api/teacher/review` в том же модуле принимает работу при наличии оценки либо отправляет на доработку по непустому комментарию. Prisma-транзакция атомарно создаёт проверку, меняет статус ДЗ, пишет аудит и системное сообщение, создаёт in-app уведомление и не дублирует feedback invite для принятых обычных уроков 5/10/15; уведомление в MAX отправляется после фиксации транзакции через общий gateway. Администратор может проверять работы любого активного ученика и при первом использовании получает teacher-профиль, .
- Аватар ученика хранится объектом в хранилище (`students.avatar_file_id`) и отдаётся тремя путями: `/api/student/me/avatar` — самому ученику, `/api/students/:id/avatar` — ему же, его преподавателям и администратору, `/api/guest/students/:id/avatar` — публично, но только для профилей со статусом `studying`, которые уже показаны в гостевой витрине. Признак `has_avatar` возвращают ответы для ученика, преподавателя, администратора и гостя; если он `false`, интерфейс оставляет прежнюю заглушку.
- У одного ДЗ может быть неограниченная лента комментариев преподавателя и ученика; комментарии не заменяют оценку и доступны только ученику-владельцу, его закреплённым преподавателям и администратору.
- Пользователь MAX сопоставляется с внутренним пользователем по `users.max_user_id`; идентификатор берётся только из подписанного initData или web-session.

## Запуск и развёртывание

```bash
docker compose up --build              # весь стек: сайт http://localhost:8080, API, бот
npm --prefix backend install && npm --prefix frontend install
npm run backend:dev                    # NestJS на 127.0.0.1:8788 (нужен DATABASE_URL)
npm run bot:dev                        # бот (нужны MAX_BOT_TOKEN и DATABASE_URL)
npm run frontend:dev                   # клиент на 5174, /api → 8788
npm test                               # e2e-тесты backend
npm run visual:test                    # визуальные тесты клиента
npm run typecheck
```

- **Docker:** переменные — в `.env` по шаблону `.env.example` или в окружении платформы (compose подставляет их в `x-app-env`); без `.env` поднимаются сайт и API, бот пишет, что `MAX_BOT_TOKEN` не задан, и завершается. Чистая сборка без кэша — около 1,5 минуты. Сервисы: `api` (NestJS, при старте создаёт схему, если база пустая), `bot` (тот же образ, `node dist/bot-main.js`), `web` (nginx со статикой клиента и прокси `/api` → `api`, порт `WEB_PORT`, по умолчанию 8080). База (и файлы при `STORAGE_DRIVER=local`) — в томе `barber-data`.
- Пустая база локально: `DATABASE_URL=file:/abs/path/barber.db npx --prefix backend tsx backend/src/database/init-schema.ts`.

## Конфигурация и секреты

Значения секретов не хранятся в репозитории. `.env` исключён из Git. Используемые переменные:

- `MAX_BOT_TOKEN`, `WEB_APP_URL`, `MAX_BOT_USERNAME` (ник бота без `@`, нужен для входа с сайта через MAX);
- `MAX_WEBAPP_AUTH` (`off`, `optional`, `strict`), `MAX_INIT_DATA_MAX_AGE_SEC` (по умолчанию сутки), `MAX_HOMEWORK_UPLOAD_MB`, `CHAT_ENABLED`;
- `STORAGE_DRIVER` (`s3`/`local`; без значения — `s3`, если задан `S3_BUCKET`), `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE`, `S3_PREFIX`, `STORAGE_LOCAL_DIR`, `STORAGE_STAGING_DIR`;
- `MAX_API_BASE_URL`, `MAX_POLL_TIMEOUT_SEC` — для тестов и отладки бота;
- `APP_NOTIFICATIONS_RETENTION_DAYS` (от 7 до 365, по умолчанию 90);
- `NEST_API_HOST` (по умолчанию `127.0.0.1`) и `NEST_API_PORT` (по умолчанию `8788`); `WEB_PORT` — порт сайта в Docker.
- `DATABASE_URL=file:/absolute/path/to/barber.db` обязателен для API и бота; поддерживается только SQLite.

**Как переменные попадают в процессы.** В Docker — через `x-app-env` в `docker-compose.yml` (значения из `.env` или окружения платформы); локально — через окружение shell.

Для production `MAX_WEBAPP_AUTH` должен быть `strict`: идентичность пользователя принимается только из initData, подписанного токеном бота. Веб-сессии хранят на сервере только SHA-256 хэш непрозрачного токена; не добавляйте токены сессий в логи или репозиторий.

## Тестирование

- `npm test` — e2e-тесты NestJS (включая бота на поддельном MAX Bot API); каждый тест создаёт временную SQLite из `schema.sql` и не трогает рабочие данные.
- `npm run visual:test` — 264 проверки клиента (скриншоты с `threshold 0` и поведение) на стенде NestJS с детерминированным сидом, см. `frontend/README.md`.
- `npm run typecheck` — TypeScript backend и frontend.

## Текущее техническое состояние

- Схема БД хранится в `backend/prisma/schema.sql`, Prisma миграциями пока не управляет.
- Бот проверен на поддельном MAX Bot API; проверку на реальном боте и мини-приложении MAX нужно провести до публикации. Всплывающее уведомление к нажатию кнопки отправляется полем `notification` в `/answers`; если MAX его не примет, текст уходит обычным сообщением.
- Служебных скриптов (выдача ролей, CLI базы, бэкап, демо-сиды) пока нет: первого администратора в Docker пока нужно назначать вручную в SQLite.

## Правила актуализации

Обновляйте этот файл в той же задаче, если меняются: архитектура, точки входа, роли/сценарии, схема БД, переменные окружения, команда запуска/деплоя, тестовый контур или значимые известные риски. Не записывайте токены, реальные ID, персональные данные, адреса внутренних серверов и содержимое `.env`. Держите текст кратким и подтверждённым кодом или документацией; при расхождении отмечайте источник истины.
